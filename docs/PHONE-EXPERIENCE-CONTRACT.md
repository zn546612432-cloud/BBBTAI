# 《熙蒙的手機》统一手机事件契约

本文件是后续 D01–D55 实施的架构约束，修改剧情之前必须确保 `tests/phone-unified-continuity.test.mjs` 和全量回归通过。

## 核心原则

1. **真正的手机，不是游戏任务板。** 每个 App 使用自己既定的原生外观。不要给手机界面增添“玩家”、关卡按钮、重复中文释义、调试说明等标签。
2. **剧情数据与运行机制分开。** 各天仅负责文本、时间、条件、回退和依赖；消息写入、未读、通知统一由 `src/services/messaging/phone-messages.js` 实现。不要在每日剧情写出 `c.messages.push` + `c.unread++` 这种私人实现。
3. **当前对话逐条送达，过去场景静默归档。** 当前有效窗口中的 NPC 气泡按现实间隔到达，同一会话共享节流。游戏时间越过窗口或换日后，一次补齐该场景所有已经成立的 NPC 前缀；遇到未发送的熙蒙台词立即停止，不能跨过它补出后续对话。保留原日期、时间和已发气泡；历史可以计未读，但不重放顶部通知，也不打断充电。
4. **未读精确、通知有序。** 玩家未打开对应会话：每条 NPC 气泡计数 +1，通知使用 `IncomingBannerQueue` 逐个呈现，聊天列表/Home 徽标读取相同 `unread` 状态；进入对应会话清零其未读，不影响其他会话。正在看该会话时，只出现聊天气泡不重复顶部横幅。
5. **熙蒙的文字绝不自动发送。** D01–D05、主线故事及将来的 D05–D55 统一从 `preset-replies.js` 提供预设输入与验证。玩家必须在原生输入框点击发送。NPC 超时/日程推进不能自动替玩家说话。焦点保持、跨 App、再次打开仍必须看见当前有效的预设；过期原话由配置的迟回分支替代，不能挡住新场景。
6. **多天统一调度。** `phone-story-scheduler.js` 注册 D01–D05。未来新增日期只登记配置与轨道，不得向 `main.js`、`story55/runtime.js` 复制每日计时器。D02–D05 使用 `lifecycle/engine.js`，D01 保留其首句自由输入、三条追问和两游戏分钟规则，通过兼容适配器归档。已完成、正在等待、旧版 dueAt/nextAt 存档原地迁移。
7. **时间和电量统一管理。** `system/runtime/policy.js` 是唯一规则源，`runtime/controller.js` 统一 tick，`time/clock.js` 只结算实际到达的游戏分钟并同步扣电。所有日期、所有 App 内现实1分钟＝游戏5分钟；仅无通知/通话/遮罩的解锁主画面挂机现实1秒＝游戏5分钟。锁屏和交互遮罩走 App 慢速；开发者界面与网页后台暂停。旧速度滑杆仅控制主画面，0暂停全局时间和普通耗电。满电900游戏分钟消耗80个百分点。消息、语音、小游戏倒计时按现实时间，不允许每日剧情覆盖时钟流速。短充保留现实1分钟最多+10%的额度、离线补电与23:59停止；不再另有短充时钟。长充保留次日08:00满电、剧情门禁与终章特殊流程。旧存档当前电量和部分耗电进度平滑保留，开发者回退日期不按时钟重算电量。
8. **KIRA 所有委托只有一个真实加密附件。** `services/commissions/attachment-flow.js` 和 `kira/features/detail/attachment.js` 是 D01–D55 唯一的附件信息与卡片显示标准。Mirage 接单后 KIRA 收到邮件，正文下方必须只有 **1 个附件**，点击先进入文件 App 原生预览，再由玩家点击 GHOST 打开。D01 与 D02 既有密钥语义保留；D03 包含 manifest 的资料统一打包成 `dataset_0521.enc`；D04 各委托也分别一个加密文件。未知邮件不凭空新增通用「查看附件 ↗」按钮，显示日期要以剧情时间为准。
9. **Mirage → KIRA 单附件 → 文件预览 → GHOST → READY TO SUBMIT → 手动提交 → 验收结算，永远只有这一套。** 每份委托仅允许调整发布者、描述、等级、报酬、有效期以及 GHOST 小游戏类型、数量和执行顺序；不能单独设计新邮件按钮、新进入 GHOST 的捷径或第二个提交按钮。D01 的无游戏部署/数据修复流程按其已约定的特殊流程执行，其余委托沿用相同文件预览入口。
10. **一周目存档不丢。** 历史聊天（2024-03-10 起）、已发消息、照片、已完成委托、奖励/账户余额与本地进度均原地保留。独立预览使用隔离命名空间；未获用户确认前不合并主分支。

## 统一服务

| 服务 | 权限与责任 |
|---|---|
| `phone-messages.js` | 写入一条气泡；去重；持久化；未读；通知；事件 |
| `phone-story-scheduler.js` | 注册各天剧情的 tick / due，入口唯一 |
| `lifecycle/engine.js` / `lifecycle/replies.js` | 统一窗口、历史补齐、迟回分支、过期、会话节流和持久进度 |
| `preset-replies.js` | 选择待发送预设文本、优先级、发送合法性 |
| `delivery.js` / `incoming-banner-queue.js` | 非剧情预定消息送达与顶部横幅队列 |
| `messaging/read.js` | 打开会话后的精确已读 |
| `kira/features/detail/policy.js` | KIRA 邮件展示授权白名单与正确日期 |
| `services/commissions/attachment-flow.js` | D01–D55 单附件元数据、权限和 GHOST 打开流程唯一入口 |
| `kira/features/detail/attachment.js` | 所有委托统一原生附件卡片，不得各天自行复制 UI |
| `story/dXX/*` | 仅当天文案、触发条件、任务规则 |

## 需要永远成立的验收测试

- D01 手动说第一句话才启动对话，不得因统一化变成自由发消息。
- D02 故事预设、一条一条 NPC 回复、D03 维修电脑和 D04 群聊均使用同一个 Send/写入规则。
- D04 胡枫给熙蒙的预设「有」必须可以看见，玩家没发就绝不出现以熙蒙名义的消息。
- D04 上午群聊不同人物连续十条：未读恰好加十；打开群聊清零。
- 同一个消息 ID 的多次 tick 不产生重复气泡/通知/收入。
- D01–D05 所有接单邮件均显示**恰好一个**与 D01/D02 样式一致、能打开的加密附件卡片（无通用「查看附件」假按钮）；点击 KIRA 卡片 → 文件预览 → GHOST。MIRAGE 只有接单和 READY TO SUBMIT，不能直接打开 GHOST。
- D01 邮件的 bank account 仍显示蓝字下划线，不做大按钮。
- 日常收件日期正确，不能一律显示「今天」。
- D01–D03、NoApp / Mirage / 银行等既有回归测试全部通过。

## 修改规范

新增场景时，先修改数据和轨道配置，再写对应回归测试。不得直接改全局 KIRA 模板去满足某个 D05 邮件；不得修改现有图像资产或替换用户给定的角色照片。任何界面样式改变都应先对照已经确定的截图、文案与上述规则。


## 聊天生命周期配置（D01–D05 已接入）

游戏分钟决定事情是否仍有效；现实毫秒只控制当前对话气泡间隔。网页后台不追赶游戏时间。现实离开十小时、游戏时间未走，不能把原话自动判成十小时后的迟回。

| 配置 | 默认与作用 |
|---|---|
| `id / chat / at / lines` | 稳定场景 ID、会话、触发游戏时间、原台词；固定 ID 不因重载变化 |
| `condition / enabled` | 剧情分支成立条件与开始条件；未发生的分支不能补历史 |
| `until / endWhen` | 时效结束；默认下一同会话场景或当日结束。群聊默认 30 游戏分钟，不能早于配置的最后历史时间 |
| `mandatory` | 必须由玩家回复的门禁，不能仅因过日子而跳过 |
| `initialDelayMs / pauseMs` | 现实气泡间隔；默认 450 / 1900 ms，各天已批准的间隔通过配置保留 |
| `historyClock / messageId / migrate` | 历史时间、兼容已有气泡 ID 与存档进度；已实际发送的时间不改写 |
| `replies.sameDay / nextDay / later / resolved` | 当天晚回、隔天、几天后、事情已解决的预设分支；可按事实返回不同台词 |
| `resolved / closed` | 事情是否解决、旧话题是否被后续事实彻底取代，不能只凭现实等候时长推断 |
| `lateDays` | 普通迟回默认 3 天；咖啡 1 天、巴黎话题 7 天；超过有效期关闭输入，不永久霸占草稿 |
| `lateReplyMinutes` | 实际发出迟回后的继续窗口，默认 60 游戏分钟；再次跳时只补已经挣得的 NPC 尾巴 |
| `unanswered` | 无回复时 NPC 的独立收尾，禁止含熙蒙消息；例如晚饭邀约后“我先去吃了” |
| `onSend / onComplete` | 只有真实发送的原场景可以触发对应结果；迟回分支不调用原邀约的成功钩子 |
| `lockChats` | 保留当前日期原先的聊天输入权限；未来日期不会被旧权限锁死 |

预设选择顺序：必须回复的场景 → 当前有效场景 → 已实际发送后的迟回延续 → 旧话题迟回；同等级优先更新日期。同一会话的当前 NPC 轮次和主线场景会暂时阻挡旧话题迟回。没有迟回配置就是不提供该回复，不复制过期原话。

### 已验证的边界

- 昨天群聊一次成为静默历史；今天的新群聊可以立即正常开始。
- 昨天的私聊只补到熙蒙未发送的位置；不自动答应邀约，不补照片、赴约事实、奖励。
- D04 晚饭 18:30 前真实发送亲吻才成立；18:31 后只提供“改天”，隔日“昨天”，多日“前几天”。迟回不会出现吃过饭的朋友圈。
- D05 胡枫已经报告电脑修好后，D03/D04 的旧维修话题使用已解决分支；衣服是否已晾以实际台词记录判断。
- D05 早饭群聊不会在熙蒙未回复时写“刚回我”。
- 重载、快速换日、开发者跳日、过期通知已在队列中、迟回到一半再跨夜均不重发、不代发。
- 首句由熙蒙主动发起而始终未发的会话，不凭空生成其历史或迟回。

相关专项回归：`tests/chat-lifecycle.test.mjs`；更改这些默认规则必须同步说明用户确认的依据。
